## הבשורה הטובה — ההפרדה זולה בהרבה ממה שנראה

בדקתי מה באמת נדרש, ומצאתי שלושה דברים שכבר עובדים לטובתנו:

1. **הסכמה נבנית מעצמה.** `admin/server/db.js:14` מגדיר `initDb()` שיוצר את **כל** הטבלאות ב-`CREATE TABLE IF NOT EXISTS`, והוא נקרא אוטומטית ב-`db.js:739-743` בכל עלייה מקומית (מדולג רק כש-`VERCEL=1`). **אין צורך בסקריפט להעתקת סכמה — היא נוצרת לבד בהפעלה הראשונה מול DB ריק.**
2. **הזריעה כבר קיימת.** `npm run seed` (`admin/server/seed.js`) יוצר את משתמש ה-`super_admin`. זה כל מה שצריך כדי להתחבר ולהתחיל לייצר סשני דמה ידנית.

## החסם היחיד שמצאתי — ודורש שינוי קוד

`admin/server/db.js:4-9` מגדיר את החיבור עם `ssl: { rejectUnauthorized: false }` — **ללא תנאי**. Postgres מקומי בהתקנת ברירת מחדל אינו תומך ב-SSL, ולכן החיבור ייכשל מיד עם `The server does not support SSL connections`.

**התיקון המינימלי:** להפוך את `ssl` למותנה בכתובת. שתי שורות:

```js
const isLocalDb = /@(localhost|127\.0\.0\.1)/.test(process.env.DATABASE_URL || '');
// ובתוך new Pool({...}):
ssl: isLocalDb ? false : { rejectUnauthorized: false },
```

**רדיוס פגיעה של השינוי הזה:** `admin/server/db.js` הוא ה-pool היחיד של כל האדמין — כל מסלול, כל שירות, כל דוח עובר דרכו. זה הקובץ הרגיש ביותר בתכנית. **לכן הניסוח חייב להיות כזה שהתנהגות פרודקשן זהה לחלוטין:** ה-`DATABASE_URL` בפרודקשן הוא כתובת Supabase, הביטוי הרגולרי מחזיר `false`, וההגדרה נשארת בדיוק `{ rejectUnauthorized: false }` כפי שהיא היום. אפס שינוי התנהגות בפרודקשן, בהגדרה.

## מה לעשות בפועל — צעד אחר צעד

1. **גיבוי:** העתק את `admin/.env` הנוכחי ל-`admin/.env.production.backup` (מחוץ לגיט, כמו המקור). זה הקובץ שאליו תחזור אם משהו משתבש.
2. **התקנת Postgres מקומי.** שתי דרכים — **זו ההחלטה שלך:**
   - **Homebrew:** `brew install postgresql@16 && brew services start postgresql@16 && createdb safecapital_dev`. מהיר, רץ ברקע תמיד, אין תקורה.
   - **Docker:** `docker run -d --name sc-pg -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres:16`. מבודד לגמרי, קל למחוק ולהתחיל מאפס, דורש ש-Docker ירוץ.

   *המלצתי: Homebrew.* אין כאן צורך בבידוד — זה DB פיתוח שאתה רוצה שיהיה שם תמיד וללא טקס.
3. **עדכון `admin/.env`:** החלף את `DATABASE_URL` ל-`postgresql://<המשתמש שלך>@localhost:5432/safecapital_dev`. **שאר המשתנים נשארים כפי שהם** — במיוחד `ANTHROPIC_API_KEY`, שאחרת המחקר לא ירוץ בכלל.
4. **שינוי הקוד** ב-`admin/server/db.js` כמתואר למעלה.
5. **הפעלה ראשונה:** `npm run dev`. `initDb()` ייצור את כל הטבלאות. ואז `npm run seed` ליצירת משתמש הניהול.
6. **זריעת נתוני דמה:** אין סקריפט זריעה לסשני וואטסאפ, ולא אמליץ לכתוב אחד בתכנית תיקון (זו הרחבה). הדרך הזולה: להיכנס לממשק וליצור 2-3 סשנים ידנית — אחד ב-`onboarding`, אחד עם סיכום ב-`research_review`, ואחד ב-`writing`. זה מכסה את כל התרחישים שהתכנית הזו דורשת לאמת.

- הרץ `npm run dev`, ואז שנה רווח בקובץ כלשהו ושמור. השרת עולה מחדש. פתח את פרודקשן בדפדפן — **הסשנים שם לא השתנו** (המונים ברשימת הסשנים זהים לפני ואחרי).

# ת2 — `A3#7`: ניקוי האתחול קוטע מחקר שרץ באמת

## מה שבור היום

`admin/server/routes/whatsapp.js:14-27` מריץ בעליית השרת:

```sql
UPDATE whatsapp_sessions SET status='research_review', updated_at=NOW() WHERE status='researching'
```

הכוונה המתועדת בהערה שמעל (`:9-13`) נכונה: לשחרר סשנים **יתומים** אחרי קריסה. הביצוע לא מבחין בין יתום לחי — הוא משנה **כל** סשן ב-`researching`, כולל אחד שרץ באותו רגע בתהליך אחר.

מכיוון שהריצה בודקת את המצב בין שאילתות (`claude-research-provider.js:326-329, 333, 345`), המחקר החי מזהה שהמצב השתנה ועוצר — **אבל הסיכום כן נבנה ממה שהספיק להיאסף.** המשתמש מקבל סיכום שנראה תקין ולא יודע שהוא חלקי.

## התיקון

להוסיף סינון לפי זמן לפסוקית ה-`WHERE`, כך שרק סשנים שלא זזו במשך זמן מוגדר ייחשבו יתומים:

```sql
WHERE status='researching' AND updated_at < NOW() - INTERVAL '20 minutes'
```

## ❓ החלטה שנדרשת ממך — אורך החלון

**הדוח המקורי הציע 5 דקות, בנימוק ש-`updated_at` מתעדכן בין שאילתות. בדקתי את הנימוק הזה והוא לא מחזיק.**

מה מצאתי: `updated_at` אכן מתעדכן אחרי **כל שאילתה שהצליחה** (`claude-research-provider.js:438-445`). אבל **בזמן שאילתה בודדת אין שום פעימת לב.** ולפי `admin/server/services/whatsapp/claude-client.js`: `MAX_RETRIES=3` (סה"כ 4 ניסיונות) × `AbortSignal.timeout(240_000)` שהוא 4 דקות, בתוספת המתנות של עד 30 שניות בין ניסיונות — **שאילתה אחת איטית שמתחדשת יכולה להימשך עד כ-17.5 דקות בלי לגעת ב-`updated_at`.**

עם חלון של 5 דקות, עלייה מחדש של השרת באמצע שאילתה איטית **תקטע מחקר חי בדיוק כמו היום.** הבאג יישאר, רק ייראה נדיר יותר — וזה הגרוע מכל.

| אפשרות | יתרון | חיסרון |
|---|---|---|
| **5 דקות** | סשן יתום משתחרר מהר | **לא סוגר את הבאג** — שאילתה איטית נקטעת |

| פעימת לב אמיתית במהלך הקריאה | מדויק | **דורש מנגנון חדש (טיימר מקביל) — זו הרחבה, לא תיקון.** לא כלול בתכנית |

**החיסרון של 20 הדקות מתקזז כמעט לגמרי על ידי ת3.** ת3 סוגר את **כל** מקרי המוות בתוך התהליך (חריגה, 0 ממצאים, כשל סיכום). אחרי ת3, ניקוי האתחול נדרש רק למוות אמיתי של התהליך — קריסה או פריסה — וזה נדיר. 20 דקות המתנה במקרה כזה הן מחיר סביר לחלוטין.

# ת3 — `A1#1` ≡ `A3#1`: סשן נתקע לנצח ב"במהלך מחקר"

## התיקון
